# mctrace

McTrace - a visual tool for working with mcstas instruments.

This project is part of a re-imagining of the mcstas core functionality. 

The main purpose of the re-imagining is to build high-level functionality directly
on top of generated code. This approach greatly reduces dependencies, and improve on the speed
and flexibility of the high-level User-facing tools.

Most importantly, it becomes possible to implement inturely new features on top
of the simulation package, including custom simulations strategies, instrument editors,
and visual run-time monitoring.

In short, monitor examply how mcstas simulates instruments in real time.

High-level functionality relies on code generated by the DSL parsing- and code
generation project, mctrace.

For more information on the mcstas/mcxtrace simulation package for materials-science
instrumentation, see mccode.org.

### simcore

There are two files: simlib.h and simcore.h. The first includes helper
libraries, and the second, the actual core runtime simulation functionality.

### development

This project is not very far along in its development, but public, mainly to 
provide conext for the re-imagining idea.

Current, notable features are:

- C++ port of monitor_nD-lib, read-table-lib (etc.) repackaged as simcore.h and simlib.h
- C++ compilation of a selection of ported components
- Runtime iniitalization of the PSI_DMC instrument
- Runtime initialization of said component and instrument code

#### Next steps: 

The mcstas simulation code always works with neutron/x-ray particles in "local coordinates"
in terms of what 3D transforms are involved.

This means that the mcstas-based 3D math is rarely, if ever, entanled with component code
(neither TRACE nor MCDISPLAY; although sometimes INITIALIZE).

This means that we can replace the geometry transforms with something more modern. 4x4 
affine matrices; the accepted standard in computer graphics for over 20 years. 

- Re-implement the system for 3D transforms between components
- Implementation of mcdisplay-calls; Output component geometries directly to the screen; rather than std-out(!)
- Simulation run-time executes correctly
- Wrap monitor calls to output data to the screen; or in any other appropriate format

If this feels like a re-implementation of "everything", keep in mind that by far most of the work
is, and always has been, done by the actual component code:

Component (and -instrument) code is where the actual physics and geometry work is
done, and the main idea of this re-imagining, is to modernize the code 
environment and thus preserve the actual physics code for future use.
